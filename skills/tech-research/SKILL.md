# 技術調査スキル

技術調査でありがちな2つの失敗を構造的に防ぐ。
1. **観点の抜け漏れ** — 思いついた分だけ調べて完結したように見せてしまう。
2. **未確認なのに断言** — 確認していないことを、確認済みの事実と同じトーンで書いてしまう。

このスキルが起動したら、以下の3フェーズを必ず順に実行する。

---

## 大原則（全フェーズ共通）

- **分からないことは「分からない」と書く。** もっともらしい生成でギャップを埋めない。埋めたくなったら、それは `[未確認]` として明示する対象。
- **すべての記述に出所ラベルを付ける**（後述）。ラベルの付かない断定文を報告に書かない。
- **直接確認していないことを、確認したかのように書かない。** 「たぶんこうなっている」を「こうなっている」と書かない。

---

## フェーズ1：着手前の観点宣言（調査を始める前に必ず出力する）

調査を始める前に、**カバーする観点**と**今回は対象外にする観点**を宣言する。宣言してからユーザーの反応を待つ必要はないが、必ず可視化してから調査に入る（ユーザーが観点の過不足に気づける）。

下のチェックリストから、今回の調査対象に該当する観点を選ぶ。該当しないものは「対象外」と明記する（黙って落とさない）。

### コードベース調査の観点チェックリスト
- [ ] **実装本体** — 対象がどこで定義され、実際の処理はどうなっているか（file:line で特定）
- [ ] **呼び出し元 / 呼び出し先** — 誰がこれを使い、これが何を使うか（依存関係）
- [ ] **データ・状態の流れ** — 入力から出力まで、どこで状態が変わるか
- [ ] **エラー / 例外パス** — 異常系・エッジケースの分岐はどうなっているか
- [ ] **設定・環境変数・フィーチャーフラグ** — 挙動を変える外部要因
- [ ] **テスト** — 何がテストでカバーされ、何が未カバーか
- [ ] **影響範囲** — これを変更すると何が壊れうるか（依存している箇所）
- [ ] **既存の慣習・類似実装** — 同種の処理が他にどう書かれているか
- [ ] **バージョン / ブランチ差異** — 見ているコードが実際に動いているものと一致するか

### 障害・原因調査の観点チェックリスト
- [ ] **再現条件** — いつ起きて、いつ起きないか
- [ ] **タイムライン** — いつから発生したか。直前に何の変更（デプロイ/設定/依存更新）があったか
- [ ] **一次情報** — 実際のエラーメッセージ・スタックトレース・ログ（要約や推測でなく実物を確認）
- [ ] **影響範囲** — どの環境/ユーザー/頻度で発生しているか
- [ ] **直接原因 vs 根本原因** — 表面的なトリガーと、その背後の本当の原因を区別する
- [ ] **外部要因** — ネットワーク・外部API・リソース枯渇・権限など、コード外の可能性
- [ ] **仮説と検証手段** — 立てた仮説それぞれに「どうすれば確認できるか」を添える

> 上記は出発点。対象に応じて観点を足してよい。ただし「足した」ことは宣言に残す。

## フェーズ2：調査の実行

- **広域検索はサブエージェントに委譲する。** 「複数ファイル/ディレクトリを横断して探す」「命名規則が不明で当たりをつける」類の検索は Explore サブエージェント（Agent ツール）に投げ、結論と file:line だけを受け取る。ファイルダンプを自分のコンテキストに直接読み込まない（調査後半での要約劣化を防ぐ）。場所が特定できてからの精読は自分で行う。
- 各発見について、**どうやって確認したか（出所）を必ず記録**する。file:line、実行したコマンド、読んだドキュメントのURL/ページ名、見たログ。
- **一次情報にあたる。** エラーの内容を推測で書かず、実際のログ・スタックトレースを確認する。コードの挙動を思い込みで書かず、実際に該当箇所を読む。
- 確認できなかった観点は、無理に埋めず「未確認」として持ち越す。
- 障害調査では、原因を1つに決め打ちする前に**対抗仮説**を1つは検討する。

---

## フェーズ3：報告（出所ラベル必須）

### 出所ラベルの体系（全記述に付ける）

| ラベル | 意味 | 付け方 |
|---|---|---|
| `[確認済: <出所>]` | 実際に読んだ/実行した/見た | 出所を具体的に。例：`[確認済: auth/session.go:142]`、`[確認済: git log]`、`[確認済: 本番ログ 2026-07-01]` |
| `[推測]` | コードや資料から論理的に導いたが直接は確認していない | 何を根拠にした推測かも一言添える |
| `[未確認]` | 確認が必要だが今回できていない | 放置せずフェーズ末の集約に載せる |

例：
> - リトライは最大3回 `[確認済: client/retry.go:28]`
> - タイムアウト時にもリトライされる `[推測: retry.go はエラー種別を区別していないため]`
> - 本番でのリトライ発生頻度 `[未確認: メトリクス未取得]`

### 報告の必須構成
1. **結論 / サマリ**（各文に出所ラベル）
2. **観点ごとの調査結果**（フェーズ1で宣言した観点に対応させる。対象外にした観点はその旨を残す）
3. **確認できなかったこと**（`[未確認]` を集約。ここを空にするために推測で埋めない）
4. **次に確認すべきこと**（未確認を潰すための具体的な手段。誰が/何をすれば確定するか）

## セルフチェック（報告を出す直前に自問する）

- ラベルの付いていない断定文が残っていないか？
- 「確認できなかったこと」セクションが不自然に空になっていないか？（空なら本当に全部確認したか疑う）
- 決め打ちした原因に対して、対抗仮説を検討したか？（障害調査の場合）
- 宣言した観点のうち、黙って落としたものはないか？
